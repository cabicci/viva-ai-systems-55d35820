# Transactional confirmed-account welcome

This slice sends one bilingual service welcome per newly confirmed auth account. It does not subscribe anyone to marketing, backfill old users, trigger on child profiles, or send offers. Recipient and immutable message content come from the server. No recipient/payload is accepted in the job request.

Apply `20260925220000_account_welcome_email.sql` through the Supabase owner after isolated rehearsal. Deploy `account-welcome-job`. Configure `ACCOUNT_WELCOME_JOB_SECRET` (at least 32 random characters), existing `RESEND_API_KEY`, verified `RESEND_FROM_EMAIL`, and optional `RESEND_REPLY_TO_EMAIL`. Keep `ACCOUNT_WELCOME_ENABLED=false` until the approved controlled test. Enable only after sender verification and release approval; invoke POST with the dedicated bearer secret from the trusted scheduler. No scheduler is created by this migration. Choose scheduling explicitly at deployment.

Every invocation claims at most five rows with a five-minute lease. SQL rechecks the confirmed email matches the captured recipient. Deleted accounts cascade-delete their outbox. The content and provider idempotency key remain constant on retries. Retries stop after 23 hours from first attempt to stay within provider deduplication; old unattempted rows stop after seven days. Inspect aged/blocked rows manually instead of replaying them automatically. Never change the v1 payload while v1 rows are retryable.

`accepted` means Resend accepted the API request, not inbox delivery. For the controlled test, verify the exact provider event and actual inbox arrival separately. Do not send to an arbitrary test address through this worker: use an approved newly confirmed account. Confirm subsequent invocations do not resend it. Read application metrics only in aggregate; do not log emails or credentials.

Rollback: disable `ACCOUNT_WELCOME_ENABLED` and stop the scheduler first. The queue can remain inert. Removing the trigger stops new queue records; do not delete auth users. Marketing journeys require their own explicit consent and release work.

## Branded and localized lifecycle (v2)

The signup form stores the adult's `full_name` and selected `preferred_locale` (`ar-EG`, `ar-MSA`, `ar-Gulf`, `en`) in Auth user metadata. Confirmation and password-reset Auth templates live in `docs/email/templates/` for the hosted Supabase Auth owner to configure. The confirmation link remains Supabase's `{{ .ConfirmationURL }}`. The brand lockup is the approved live PNG at `/brand/masaarat-logo-lockup.png`; it is decorative and the message remains readable without images. Auth templates and Resend Auth SMTP settings require separate live configuration and a real delivery test; committing HTML files does not change Supabase Auth.

`20260925230000_branded_account_mail.sql` preserves existing v1 welcome rows and payloads, and captures name/locale for future v2 confirmations. New v2 messages use a distinct idempotency key. After an applied, verified Stripe **test** payment transition, it also queues one subscription service notice per paid event. Rejected, stale, duplicate, unpaid Checkout and admin grants do not queue mail. Confirmation and renewal have distinct localized copy. Names are escaped in HTML; unsupported or missing locales fall back to ar-EG and missing names to a generic greeting. The outbox rechecks the confirmed email and current paid plan; no email uses a browser-supplied price, role, or plan. The notice is not a payment receipt.

Deploy the new migration before the updated worker. `SUBSCRIPTION_MAIL_ENABLED=false` must stay unset/false until Stripe payment and confirmation templates have controlled tests and owner approval for customer sends. Keep `ACCOUNT_WELCOME_ENABLED=false` until a new confirmed account proves API acceptance, actual delivery, inbox receipt, and no duplicate. Existing scheduler uses the same worker endpoint; no duplicate cron job is needed. Kids release and live payments have independent gates; do not imply that this sends Kids billing mail before a verified Kids payment event exists. Keep marketing journeys separate with their own consent and unsubscribe handling. For hosted Supabase Auth, configure custom SMTP using the verified `mail.masaarat.ai` sender before customer signup confirmation; never disable email confirmation to work around SMTP.
