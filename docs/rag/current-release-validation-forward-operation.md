# Current-release validation forward operation

This PR records a guarded forward database correction and bounded operator diagnostics. It does not execute SQL, enable an index/worker, publish the website or change billing/authentication. The source/performance repair has been verified on the isolated test backend; this is not evidence it has run on another deployment.

Before application, the release owner must verify the intended existing backend binding and its actual catalog/permissions. Never copy the private test project's environment/target guards into this repository. Matching routine hashes alone does not prove the external project identity. No key is supplied through these scripts or chat.

Use the existing managed migration history and reviewed baseline first, including current-release and automatic-job prerequisites. Do not apply both the archived Supabase migration family and the managed Drizzle family; do not reapply old CREATE TABLE scripts to fill a partial installation. The forward operation is deliberately outside migration auto-discovery and has no invented journal entry. A clean installation needs this reviewed forward operation after its matching baseline; the historical baseline alone retains the old validation strategy.

Stop index/provider/automatic work safely and reconcile outstanding requests through existing receipts/state; do not force-clear a lease or repeat an uncertain paid attempt. Capture routine identities/body hashes/owner/ACL/config and current execution/batch/request/row counts. Both forward and rollback candidates refuse any inflight current batch or running automatic job, different body hashes or unexpected routine configuration.

Apply `scripts/rag/current-release-validation-performance-candidate.sql` once through the existing genuine operator, only after its target-specific review. It is one atomic DO replacing three existing routine bodies. It preserves signatures, service authority, all validation/cardinality/source/index-state conditions, transactions/locks/request/lease/budgets and the existing60s per-function timeouts. Its postcheck compares all routine metadata except body, and its fixed new body hashes. It does not manipulate any data or index state. A trailing status query is not a substitute for success of the DO itself. If the exact new definitions are already installed, verify them instead of rerunning the guarded old-to-new operation.

Independently re-read catalog and data/lease/request counts after application. Install the matching reviewed application source through the normal release process, then verify its compiled source identity before a separately authorized bounded canonical index operation. SQL function signatures are unchanged, so the diagnostic code is compatible with the before/after SQL; applying the reviewed SQL first avoids paying for a batch against the old slow validator. This sequence itself authorizes no production mutation or website publication.

The compiled indexer fingerprint changes from the parent source because executor.server.ts is one of the existing eight fingerprint inputs. This does not reset the content-addressed current release/execution. Future automatic manifest/job keys include that fingerprint: old queued rows remain stored but are not selected by the new key set; active old leases are not automatically invalidated solely by build hash. Existing live/expired/held paid-request safeguards still apply. A new fingerprint does not migrate jobs, bypass uncertainty, activate an incomplete index or guarantee zero embedding cost. Require actual quiescence before replacing the runtime; do not alter the fingerprint to hide the change.

If reverting the database correction, establish the same genuine target and safe quiescence, capture the current catalog, and use `scripts/rag/current-release-validation-performance-rollback-candidate.sql`. It strictly requires the exact new definitions/config and atomically restores the three old bodies/metadata. Independently verify the old catalog afterward. Code rollback restores only the reviewed source preimages and removes only these added files through the normal release process. Neither rollback undoes charges, erases requests/jobs/vectors, makes a consumed request reusable or guarantees an active predecessor. Do not rerun a whole historical migration as rollback.

The diagnostic intermediate must not be published alone as proof of the performance correction. Runtime success, complete indexing, answer/citation behavior and all-curricula coverage remain separate acceptance checks. Payment/email/commerce/auth source and their installed state are outside this correction.
